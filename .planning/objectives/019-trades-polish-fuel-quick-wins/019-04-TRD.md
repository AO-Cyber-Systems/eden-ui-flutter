<objective>
Ship `EdenFuelCardPaymentEntry` — the fuel-card-specific payment entry widget closing the fuel vertical's #1 competitive gap per `USE_CASES_FUEL_2026-05-17.md` Rec #1: "the ONLY widget-shaped capability gap with competitive consequences. Without fuel-card support, Eden Biz cannot serve commercial / fleet-fueling segment — the highest-margin customer base."

Closes UC-E3 (driver collects payment on delivery via fuel card). Composes obj 012-03 `EdenPaymentEntry` + obj 011-08 `EdenSecretField.classified` (PCI-aware PAN entry) + obj 001-10 `EdenFormWizard` (4-step flow).

Per use-case docs: "FleetCor / Wex / Voyager / EFS cards have specific PIN flows + odometer prompts + driver IDs that the generic EdenPaymentEntry doesn't surface. Industry-standard: ISO 8583 fleet-card extensions." This widget codifies the network-specific prompt shapes as declarative `EdenFuelCardPromptSpec` value classes.

Cross-vertical: deliberately fuel-card-specific (per Rec #1 framing), but generic over which network via the `EdenFuelCardNetwork` enum. Could conceivably extend to retail-fuel cardlock (FuelCloud integration) by consumer supplying custom `promptsOverride`.

Outside-in test approach: static rendering tests (renders 4-step wizard with Step 1 active), then per-network prompt resolution tests (selecting fleetCor surfaces correct prompts), then full flow tests (swipe → prompts → amount → submit emits correct draft), then PCI scope tests (only last-4 retained in draft).

One test at a time per habit 3. RED → GREEN → next test.
</objective>

<anti_patterns>
- **Do NOT store full PAN in draft.** Only last-4 retained. Per PCI DSS scope reduction, the full PAN is consumer-handled (tokenized by their payment processor). The widget never persists or emits the full PAN.
- **Do NOT auto-validate Luhn checksum.** Card-number validity is the payment processor's job. Widget accepts whatever PAN the user enters; processor rejects invalid ones downstream.
- **Do NOT include actual fuel-card network SDK calls.** No `wex_merchant_sdk`, no `fleetcor_api`. All network communication is the consumer's backend job; widget emits the draft.
- **Do NOT eat the back-button.** EdenFormWizard handles navigation; system back works normally.
- **Do NOT call onSubmit on step navigation.** Only on the final Submit button in Step 4.
- **Do NOT mix prompts across networks.** If `network == fleetCor`, show fleetCor's default prompts (or `promptsOverride` if supplied). Do NOT show prompts from other networks even if the user later changes network.
</anti_patterns>

**Design (locked):**

Value classes per the must-haves. Network prompt-spec table is the canonical FleetCor / Wex / Voyager / EFS / generic mapping. PCI scope: only last-4 retained.

**Cross-vertical sample scenarios for catalog:**

1. **FleetCor card** — driver Bob (driverId='BOB1234'), vehicle 'TRUCK-12', odometer 84,521, trip 'WK-2026-19'.
2. **Wex card** — driver Sue (driverId='SUE5678'), odometer 124,300.
3. **Voyager card** — driver Mike (driverId='MIKE99'), vehicle 'TRUCK-22', custom 'PROJ-A47'.
4. **EFS card** — driver Joe (driverId='JOE5'), vehicle 'TRUCK-14', odometer 56,000.
5. **Generic card** — driver name only, no vehicle.

**Why declarative prompt-spec approach:** ServiceTitan-class systems hardcode the prompts per network in service classes; our library exposes them as declarative value classes so consumers can:
- Override per tenant (some FleetCor accounts disable tripNumber).
- Extend with custom site-prompts (Voyager supports up to 6 custom prompts per merchant).
- Plug in new networks without library changes (e.g., adding Comdata via `promptsOverride`).
</context>

## Test list

**Static rendering**
- `EdenFuelCardPaymentEntry(network: EdenFuelCardNetwork.fleetCor, onSubmit: noop)` renders a 4-step wizard.
- Step 1 ('Card') is active by default.
- Step 1 renders `EdenSecretField` (classified or fallback) for PAN entry.

**Network-specific prompt resolution (Step 2)**
- `network: fleetCor` → Step 2 shows 4 prompts (driverId, vehicleId, odometer, tripNumber); first 3 required, last optional.
- `network: wex` → Step 2 shows 3 prompts (driverId, odometer, purchaseDeviceId).
- `network: voyager` → Step 2 shows 3 prompts (driverId, vehicleId, customPrompt1).
- `network: efs` → Step 2 shows 4 prompts.
- `network: generic` → Step 2 shows 2 prompts.
- `promptsOverride: customList` → Step 2 shows ONLY the override prompts (replacement, not merge).

**Step 1 — Card swipe vs manual**
- `onSwipeCard: null` → only manual PAN entry visible.
- `onSwipeCard: cb` → 'Swipe card' button visible above manual entry; tap → calls `cb(context)` → PAN populated → auto-advance to Step 2.
- Enter 16-digit PAN → last-4 displayed in clear ('•••• 1234'); full PAN never displayed after entry.
- Next button disabled until PAN last-4 has length 4.

**Step 2 — Prompts**
- Required prompts gate Next button: leave driverId empty → Next disabled; fill → Next enabled.
- numericPin kind renders `EdenSecretField` (obscure); text kind renders `EdenInput`; odometer kind renders `EdenInput` with numeric keyboard + min=0 validation.
- Filling prompt fields updates `_promptValues` map.

**Step 3 — Amount**
- Composes `EdenPaymentEntry` from obj 012-03.
- `prefilledAmount: 245.50` → initial amount value is 245.50.
- Edit amount → `_amount` state updates.
- Next disabled when `_amount <= 0`.

**Step 4 — Confirmation**
- Renders summary: network label, masked PAN ('•••• 1234'), prompt values, amount.
- Submit button → calls `onSubmit(draft)` with correct draft.
- Cancel button → calls `onCancel`.

**Draft assembly**
- Submitting a fleetCor flow with PAN '4111111111111234', driverId='BOB1234', vehicleId='TRUCK-12', odometer='84521', amount 245.50 → emits `EdenFuelCardPaymentDraft(network: fleetCor, panLast4: '1234', promptValues: {'driverId': 'BOB1234', ...}, amountUsd: 245.50)`.
- promptValues map keys match the resolved prompt fieldKeys.
- panLast4 ALWAYS 4 chars even if PAN < 4 (zero-pad).

**PCI scope**
- Draft never contains the full PAN (only last-4).
- Inspecting widget state after Step 1 → no `_fullPan` field exposed publicly; PAN lives only in the controller buffer that is cleared on dispose.

**Cross-vertical**
- All 5 networks render through full flow without errors.

**Responsive — iPhone-narrow (390pt)**
- Wizard renders without overflow.
- PAN entry full-width; prompts stack vertically.

**Theme-profile aware**
- Wrap in `EdenAdaptiveTheme(profile: EdenThemeProfile.commercialWarm)` → status colors from palette.
