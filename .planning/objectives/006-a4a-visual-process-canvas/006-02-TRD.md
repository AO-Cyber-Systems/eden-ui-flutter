<objective>
Wave 1, second leg. Extend the existing `EdenDiagram` canvas engine with the three capabilities the process-builder port needs but the current engine lacks: (D-1) drop-target hit-testing on screen coordinates, (D-2) drop-target visual highlight, custom-widget node rendering (each node becomes a consumer-provided Widget tree, not a CustomPainter shape), and multi-handle port support (E-5) honoring `EdenDiagramNode.ports` (added in TRD 01).

These are **additive** extensions — the existing system-diagram demo (`lib/dev_app/screens/diagram_screen.dart`) and its CustomPainter-rendered nodes keep working unchanged. The new capabilities opt in via new optional parameters on `EdenDiagram`.

After this TRD ships, TRD 14 (`EdenVisualProcessCanvas`) can compose the process-builder widgets on top of `EdenDiagram` without re-implementing canvas pan/zoom/edge-routing/grid logic.
</objective>

<context>
**Locked design inputs (do NOT revisit):**
- Existing `EdenDiagram` at `lib/src/widgets/eden_diagram/eden_diagram.dart:26-365` — uses CustomPaint with `_TransformPainter` delegating to `EdenDiagramPainter`. Pan/zoom/grid/edge-routing all in place.
- Existing hit-test at `eden_diagram.dart:90-98` (`_hitTestNode(Offset canvasPos)`) — currently PRIVATE to `_EdenDiagramState`. This TRD exposes a public flavor.
- Existing `EdenDiagramPainter._drawNode` at `diagram_painter.dart:59-193` — renders ALL nodes as CustomPainter shapes. This TRD adds the "skip CustomPainter rendering when customNodeRenderer is provided; render Widget tree at node bounds instead" branch.
- TRD 01 shipped `EdenDiagramPort` value type + `EdenDiagramNode.ports: List<EdenDiagramPort>?` field. This TRD wires it into the canvas (hit-test, port-dot rendering, edge anchors).
- Donor `VisualProcessCanvas.tsx:464-507` — `findNodeAtPosition(clientX, clientY)` + `handleDragOver` set `dropTargetNodeId` and React Flow re-renders with `isDropTarget: node.id === dropTargetNodeId`. Library equivalent: parent widget owns `DragTarget`, sends screen-coord drag updates to `EdenDiagram` via a new `onDragUpdate(Offset screenPos)` API; the canvas converts screen → canvas, hit-tests, and fires `onDropTargetChanged(nodeId?)`.

**Decomposition principle (per Constraint 13 of OBJECTIVE.md):** the donor's React-Flow integration is verbose because it wraps `@xyflow/react`. Library has direct ownership of the canvas, so the same logic compresses significantly. Target: ≤200 LOC of additions to `eden_diagram.dart` + `diagram_painter.dart` combined.

**Custom-widget node rendering approach:**
- Option A — Stack of positioned widgets on top of the CustomPaint, each at node x/y. Simple, works with Flutter widget tree (hit-test, gesture detection, accessibility tree all native).
- Option B — Have CustomPainter render placeholder rects, parent stacks consumer widgets via Stack+Positioned. More code, no advantage.

**Chosen: Option A.** When `customNodeRenderer != null`:
- CustomPaint draws grid + edges + drag-edge preview + port dots ONLY (NOT nodes).
- `EdenDiagram._EdenDiagramState.build` adds a `Stack` overlay above the CustomPaint with `Positioned(left: panOffset.dx + node.x * scale, top: panOffset.dy + node.y * scale, width: node.width * scale, height: node.height * scale, child: Transform.scale(scale: scale, child: customNodeRenderer(node)))` for each node.
- Pan/zoom transform applied via the Positioned offsets + Transform.scale (NOT via Matrix4 on the Stack, which would break hit-test).
- Node dragging still works: the Listener captures pointer events on the Stack via `IgnorePointer` toggling — consumer widget gets pointer events when in select mode (for context menu / inline editing); the canvas captures them in pan mode.

**Drop-target hit-test approach:**
- New `EdenDiagram.onDragUpdate(Offset screenPosition)` public method (callable from parent's `DragTarget.onMove`).
- Converts screen → canvas via existing `_toCanvas` logic, runs hit-test, fires `widget.onDropTargetChanged(node?.id)` when the hit changes.
- New `EdenDiagram.onDragLeave()` clears: fires `onDropTargetChanged(null)`.
- New `EdenDiagram.hitTestNode(Offset screenPosition) → EdenDiagramNode?` — public sync hit-test for the parent's `DragTarget.onAcceptWithDetails` to find the drop target.
- The canvas itself does NOT own the DragTarget — parent does. This keeps `EdenDiagram` framework-agnostic (drag-from-toolbox source lives in TRD 12; canvas is the drop target).

**`isDropTarget` rendering:**
- When using CustomPainter (no customNodeRenderer): add `dropTargetNodeId: String?` to `EdenDiagramPainter` constructor; `_drawNode` checks `node.id == dropTargetNodeId` and adds the primary-color ring (mirrors selected-node ring at higher alpha).
- When using customNodeRenderer: the renderer is responsible for rendering its own drop-target state. Library exposes the `dropTargetNodeId` to the renderer via `EdenDiagramNodeContext` (NEW value type passed into the renderer).

**Multi-handle port support:**
- `EdenDiagramNode.ports != null` → canvas uses these instead of legacy 4-direction model:
  - Hit-test for port (in `_hitTestPort`): iterate `node.ports!` and check distance to each port's pixel position (`node.x + node.width * port.offset` for top/bottom; `node.y + node.height * port.offset` for left/right).
  - Render port dots (in `EdenDiagramPainter._drawNode`): draw a dot per port at its computed pixel position, colored by `port.color ?? theme.colorScheme.primary`.
  - Edge anchor lookup: `EdenDiagramEdge.sourcePort / .targetPort` is an `EdenPortSide` enum today. When source/target node has custom ports, also support a NEW field `EdenDiagramEdge.sourcePortId / .targetPortId: String?` that, when set, looks up the port by id and uses its computed pixel position. Backward compat: if `sourcePortId` is null, fall back to `sourcePort` enum (legacy behavior).

**Scale + Transform interaction (CRITICAL gotcha):** when `customNodeRenderer` is provided, the Stack overlay's `Positioned` math MUST apply the same pan + scale as the CustomPaint. A naive `Transform(matrix4: ...)` wrapper around the Stack would work for drawing but BREAKS hit-test because Flutter's hit-test pipeline doesn't pre-transform pointer positions for Transform widgets. Solution: compute the on-screen `left`/`top`/`width`/`height` in pixel terms for each `Positioned` (applying pan + scale manually) and wrap the renderer in `Transform.scale(scale: scale, alignment: Alignment.topLeft)` so text/icons inside the node scale visually. The Listener on the canvas still owns pan/zoom gestures.
</context>

<gotchas>
- **Hit-test must respect z-order.** Existing `_hitTestNode` iterates `nodes` in reverse (last = topmost). Preserve this. New public `hitTestNode(Offset screen)` converts screen → canvas first, then runs the same reverse-iteration.
- **Drop-target ring color.** Use `theme.colorScheme.primary.withValues(alpha: 0.5)` for the ring + `withValues(alpha: 0.3)` for the fill tint. Match donor PhaseNode.tsx:70 `border-blue-500 ring-2 ring-blue-500/30`.
- **Custom renderer + selection ring.** When `customNodeRenderer != null`, the library does NOT draw the selection ring (the renderer is responsible for its own visual selection state). Library passes `selected: bool` and `dropTarget: bool` through `EdenDiagramNodeContext`. Consumers MUST render their own ring if they want one.
- **Pan/zoom math for Stack overlay.** Each `Positioned`:
  ```dart
  Positioned(
    left: panOffset.dx + node.x * scale,
    top: panOffset.dy + node.y * scale,
    width: node.width * scale,
    height: node.height * scale,
    child: Transform.scale(
      scale: scale,
      alignment: Alignment.topLeft,
      child: SizedBox(
        width: node.width,
        height: node.height,
        child: customNodeRenderer!(node, context),
      ),
    ),
  )
  ```
  The double-application (Positioned width = node.width * scale + Transform.scale = scale) is intentional: Positioned gives correct screen position, Transform.scale makes text/icons inside the node scale visually.
- **IgnorePointer toggling for dual-mode hit-test.** When `tool == EdenDiagramTool.select` and a `customNodeRenderer` is in use, the consumer's widgets should receive pointer events (for click-to-edit popovers, context menus, etc.) — wrap the Stack in `IgnorePointer(ignoring: false)`. When `tool == pan` or `connect`, library captures pointer events at the canvas Listener — wrap the Stack in `IgnorePointer(ignoring: true)`. Node-drag in select mode is captured at the Listener level when the pointer lands on a node but NOT on an interactive sub-widget; rely on the `gesture-arena` Flutter mechanic to resolve.
- **Edge anchor lookup with custom ports.** Add `String? sourcePortId` and `String? targetPortId` to `EdenDiagramEdge` (additive — defaults null). In `_drawEdge`, before using `sourcePort` enum, check `if (sourcePortId != null && sourceNode.ports != null) { final port = sourceNode.ports!.firstWhere((p) => p.id == sourcePortId, orElse: null); if (port != null) use port-position; else fall back to sourcePort enum; }`. Document the fallback in dartdoc.
- **`EdenDiagramNodeContext` value type.** Lightweight class passed to `customNodeRenderer`:
  ```dart

      required this.node,
      this.selected = false,
      this.hovered = false,
      this.dropTarget = false,
    });
    final EdenDiagramNode node;
    final bool selected;
    final bool hovered;
    final bool dropTarget;
  }
  ```
  Pass into renderer signature: `Widget Function(EdenDiagramNodeContext context)?`.

- **Mermaid parser back-compat.** `mermaid_parser.dart` constructs `EdenDiagramNode` instances without `ports`. No change needed — `ports` defaults null.
- **Existing diagram_screen.dart back-compat.** It uses `EdenDiagram(data: data)`. Don't break it. Re-run the dev catalog after this TRD lands as a manual smoke (or use the back-compat regression test from TRD 01).
- **Custom-renderer file size.** If `_EdenDiagramState.build` grows significantly, extract the Stack-overlay logic into a private `_buildNodeOverlay()` helper. Keep `build` readable.
- **Don't introduce a separate widget for custom-rendered nodes.** Keep it inline in `_EdenDiagramState.build`. A `_NodeOverlayItem` widget would be premature abstraction.
</gotchas>

## Test list (write FIRST — RED before any GREEN code)

**Drop-target hit-test API**
- `EdenDiagram.hitTestNode(Offset screen)` returns the topmost node at the given SCREEN coordinate (factoring pan + zoom). Test with a fixture diagram: at `Offset(150, 50)` returns the node bounded by `(100, 0, 200, 60)` after default zoom/pan; at `Offset(500, 500)` returns null (empty space).
- `EdenDiagram.hitTestNode` respects z-order: with overlapping nodes, returns the last-drawn (topmost).
- `EdenDiagram.hitTestNode` returns null when canvas pan/zoom places the cursor outside any node bounds.

**onDragUpdate + onDropTargetChanged callback**
- A `GlobalKey<EdenDiagramState>` (or analogous) lets parent code invoke `state.onDragUpdate(screenOffset)`. After invocation with a position over a node, `onDropTargetChanged(nodeId)` fires once with the node's id.
- Calling `onDragUpdate` with the same drag-over position twice fires `onDropTargetChanged` only ONCE (de-dup; matches donor's `setDropTargetNodeId((prev) => prev === newTarget ? prev : newTarget)`).
- Calling `onDragUpdate` with a position over a DIFFERENT node fires `onDropTargetChanged(newNodeId)`.
- Calling `onDragUpdate` with a position over empty space (no node) fires `onDropTargetChanged(null)`.
- Calling `onDragLeave()` fires `onDropTargetChanged(null)` (idempotent — calling twice fires once).

**dropTargetNodeId visual ring (CustomPainter path)**
- When `EdenDiagram(data: fixture, dropTargetNodeId: 'phase-1')` (passed via state setter), the painter draws a primary-color ring around the node with id `phase-1`. Pumps + pixel-test-free: assert by inspecting `EdenDiagramPainter` constructor args via `find.byType(CustomPaint)` + delegate inspection.
- When `dropTargetNodeId: null`, no ring is drawn.
- Selected + dropTarget combined: dropTarget ring takes visual priority (renders OUTSIDE the selected ring) — assert via painter call sequence.

**customNodeRenderer — opt-in rendering**
- `EdenDiagram(data: fixture, customNodeRenderer: (ctx) => Container(key: ValueKey('node-${ctx.node.id}'), color: Colors.red))` renders one `Container` per node in the diagram.
- Stack overlay positions each Container at `Positioned(left: node.x, top: node.y, width: node.width, height: node.height)` AFTER pan/zoom transform applied. Hit-test on the rendered Container at the node's expected screen position works.
- When `customNodeRenderer != null`, CustomPainter does NOT draw node shapes (verified by checking no fill drawn at node centers — assert via painter call count).
- `customNodeRenderer` receives the correct context: `ctx.node.id` matches, `ctx.selected == false` initially, `ctx.dropTarget == false` initially. Selecting a node (tap) updates `ctx.selected` on next render.

**EdenDiagramNode.ports — hit-test for ports**

The canvas's port-hit-test (state-internal) finds the 'yes' port at canvas position `Offset(200, 150)` (right side center).

**EdenDiagramNode.ports — port-dot rendering**
- A node with 2 custom ports renders 2 port dots (visible when node is selected/hovered).
- A node with 4 legacy ports (no custom ports list) renders 4 port dots (back-compat).
- Port dot color: when `port.color == null`, uses `theme.colorScheme.primary`; when `port.color == '#10B981'`, parses hex and uses Color(0xFF10B981).

**EdenDiagramEdge.sourcePortId / .targetPortId — edge anchor with custom ports**

Assert by inspecting `EdenDiagramPainter` start-point computation via a probe.
