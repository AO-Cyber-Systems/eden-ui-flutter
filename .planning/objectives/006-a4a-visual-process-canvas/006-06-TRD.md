**Inline task list rendering:**
Each task row renders as a small Container with:
- Row 1: `[#]` (1-indexed sort number) + task displayName (clickable for inline rename) + hover-show actions (ChevronUp/ChevronDown reorder, Settings2 advanced-edit, Trash delete)
- Row 2: 4 inline toggle dots (Req/Photo/Sig/Approve) shown when not editing; toggling fires `onUpdateTask(taskId, {fieldName: !current})`
- Optional Zap icon if any task-level workflow hook set

**Drag-target for task split:**
Each task row is itself a DragTarget for drag events of `application/process-task-source`. When a task is dragged from the toolbox (TRD 12) onto a task row inside a different group's expanded list, the canvas (via TRD 14 composer) fires `onSplitTaskToNewGroup(draggedTaskId, parentPhaseId)`. This TRD only renders the visual highlight (`dropTargetTaskId == task.id`) and exposes the drop-target detection at the widget level via a callback.

**Task reorder:**
ChevronUp swaps current task's sortOrder with the previous task's; ChevronDown with the next. Implementation: dispatch TWO `onUpdateTask` calls (matches donor `handleMoveTask`). Library callbacks fire in sequence; consumer's debouncer (if any) flushes both updates.

<gotchas>
- **Inline task list height grows dynamically.** When expanded, the group node height should be `headerHeight + addRowHeight + (tasks.length * taskRowHeight)`. The graph builder (TRD 03) sets a default height of 80; the swimlane layout (TRD 08) overrides per-group height based on task count (already accounted for in the donor `applySwimLaneLayout`). Library v1: the node widget renders the full list inside its allocated box and lets clipping occur if box is too short. TRD 08 layout will allocate enough height.
- **`group.taskGroupTemplateId != null` indicates an imported template** — render `Icons.menu_book` instead of `Icons.folder` for the header icon. Donor uses Lucide `BookTemplate`.
- **`isCollapsedDefault: bool`** on the group — initial expand/collapse state. Widget state inits from `group.isCollapsedDefault ? false : true`. After mount, the state is widget-local (no controller plumbing needed for v1 — donor matches this).
- **Workflow-hooks Zap icon:** show `Icons.bolt` (amber) when any of these are non-null:
  - group.onAllCompleteWorkflowId
  - group.onItemNaWorkflowId
  - group.onItemCantDoWorkflowId
  Per task: show small amber Icons.bolt if any of `onCompleteWorkflowId`, `onBlockedWorkflowId`, `onNaWorkflowId`, `onCantDoWorkflowId` non-null.
- **Add button at bottom of header (before tasks list):** "Add" text + Plus icon. Tapping fires `onAddTaskInGroup(group.id, {'runtimeComponent': 'checklist'})` per donor default.
- **Task drop-target visual:** when `dropTargetTaskId == task.id`, the task row gets `border-blue-500 bg-blue-50` (light-mode); in Flutter, `border: Border.all(color: theme.colorScheme.primary), color: theme.colorScheme.primary.withValues(alpha: 0.05)`.
- **Drag-and-drop wiring:** the task row is a `DragTarget<String>` (drag data is the source task type). On `onWillAccept`, set `_dropTargetTaskId = task.id`. On `onAccept`, fire `onSplitTaskToNewGroup(draggedTaskId, group.processPhaseId)`. The drag SOURCE lives in TRD 12 (`EdenProcessToolbox`); this widget only handles being a target.
  - Simpler v1: expose a `void onTaskRowDragOver(int taskId)` + `void onTaskRowDragLeave()` callback for the canvas composer to wire up via parent DragTarget. Or: directly use `DragTarget` inside the widget. Pick `DragTarget` — keeps widget self-contained.
- **`Draggable<String>` data convention:** the canvas composer (TRD 14) and toolbox (TRD 12) agree on the drag-data shape — `'task'` for a fresh task, `'task-existing:${taskId}'` for an existing task being dragged from another group. Document in dartdoc on EdenProcessTaskGroupNode.
- **Reorder buttons disabled at boundaries:** ChevronUp disabled when first task (idx==0); ChevronDown disabled when last.
- **Inline rename across multiple tasks:** only ONE task can be in edit mode at a time. State: `int? editingTaskId`. When entering edit on task 5, exit edit on whatever was before.
- **`_useUpdateNodeInternals` analogue:** donor uses React Flow's `useUpdateNodeInternals` to recompute node bounds when toggling expand state (since the node grows/shrinks). Library equivalent: rely on `LayoutBuilder` / `IntrinsicHeight` — `Stack` overlay positions are set per-node by graph builder + layout, and `EdenDiagramNode.height` doesn't auto-recompute. For v1, the height is FIXED based on `tasks.length` at canvas-build time; expand/collapse changes the VISUAL height but NOT the diagram-node `height` field. Document this trade-off: expanded → potentially clipped; collapsed → unused space. Real fix lands when layout becomes truly dynamic (post-v1).
- **The widget's content can exceed its parent Box.** Wrap the inline task list in `Flexible(child: SingleChildScrollView(...))` to allow vertical scroll within the node when the visible height is less than content height.
</gotchas>
