# 024-02 — The envelope and the decoders

## BINDING CONTRACT (repeated per objective rule)

1. The renderer never fetches. 2. Affordances are granted by the payload.
3. Actions bind to tool ids or proposal ids, NEVER routes. 4. Refusal is
one-sided. 5. What this layer cannot do honestly becomes a refusal — never a
guess, never a crash. 6. §22: a check whose failure mode is indistinguishable
from its success mode is not a check.

## The comment this TRD must amend, not contradict

`lib/src/widgets/eden_data_display/agent_intent_data.dart` says:

> NO JSON DECODER LIVES HERE, DELIBERATELY. A `fromJson` in this package
> would be a second, untested transcription of the wire format sitting next
> to the first; the mapping from `StructuredContent` to these classes belongs
> to whichever consumer owns the transport, where it can be tested against
> the recordings themselves. What this file owns is the SHAPE.

That reasoning was sound and its condition is now met: 024-01 vendored the
recordings and gated them, and this layer becomes the transport owner. The
decoder is tested against those recordings. **Amend that comment in this
TRD** — pointing at the new library and saying what changed — rather than
leaving it asserting the opposite of the file beside it. A stale comment that
contradicts the code is how the next reader learns to distrust all of them.

## Shape

`EdenAgentIntent { String componentId; Object? data; List<EdenRawAction> actions }`
with `fromJson`. `data` stays RAW here — decoding to typed data is the
decoder's job, and keeping them separate means a malformed `data` cannot stop
the envelope from being read well enough to name the component that failed.

`EdenRawAction { String id; String? toolId; String? proposalId; String? decision }`
— all three bindings nullable, because `agentintent.Action` is ONE Go struct
with `tool_id`, `proposal_id` and `decision` all `omitempty`. The wire permits
an action bound to nothing and one bound to both. The envelope represents
that faithfully; deciding what is bindable belongs to the decoder and the
components, which already refuse an empty `decision` and a mismatched
`proposal_id`.

Decoding returns a RESULT, never throws:
`EdenIntentDecodeResult` = either typed data, or a refusal carrying a reason.

## TEST LIST (written before any test code)

### Envelope
1. `fromJson` over fixture 01 yields `componentId == 'list/appointments'` and
   2 actions with the recorded ids.
2. An action with only `tool_id` leaves `proposalId`/`decision` null; an
   action with only `proposal_id`+`decision` (fixture 05) leaves `toolId`
   null. Both shapes survive the round trip — neither is normalised away.
3. A missing `component_id` is a refusal naming the field, not a throw.
4. `actions` absent entirely decodes to an EMPTY list, not null — "the
   payload granted nothing" is read-only, which is a real state (contract 2).

### Decoders — one per component, each over its own vendored fixture
5. `list/appointments` over fixture 01 → 5 rows; `notes` present on exactly
   the rows the recording has it on and null elsewhere. **Absence is modelled,
   not smoothed** — a decoder defaulting it to `''` would make the nullable
   field pointless.
6. `list/appointments` over fixture 02 → an empty list, decoded successfully.
   Empty is an answer, not a failure.
7. `error/refusal` over fixture 03 and 14 → the recorded reason, verbatim.
8. `list/customers` over fixture 11 → 2 rows, both hints
   `p***@example.test`, displayed as received.
9. `list/services` over fixture 08 → 1 row, `priceCents == 5000`.
10. `card/proposal` over fixture 05 → `actionId`, `applied == false`,
    `status == 'pending_approval'`, `expiresAt` parsed as the recorded UTC
    instant.
11. **Every one of the 14 fixtures decodes to either typed data or a refusal
    — none throws.** Iterate the whole vendored set. This is the case that
    catches a fixture nobody wrote a decoder for.

### Refusals — the half that must not be a guess
12. An unknown `component_id` → refusal naming the id.
13. A missing required key → refusal naming the component AND the field.
    Built by MUTATING a vendored fixture (delete `email_hint` from fixture
    11), stated in the test as such.
14. A wrong JSON type (`price_cents` as a String) → refusal naming the field,
    not a crash and not a coerced 0. A silent coercion renders a plausible
    wrong price, which is contract 5 exactly.
15. An unparseable RFC3339 instant → refusal naming the field.
16. **A refusal carries ZERO actions** (contract 4), even when the input
    payload carried two. A refusal that kept the actions would offer controls
    for an observation that failed.

## Fixtures

Vendored recordings from 024-01. Where a case needs a payload no recording
contains (13, 14, 15), build it by MUTATING a named fixture in a factory
function and say in the test which fixture and what was changed. No invented
payloads.

## Differential controls (required)

- Make the missing-key path coerce to a default instead of refusing → expect
