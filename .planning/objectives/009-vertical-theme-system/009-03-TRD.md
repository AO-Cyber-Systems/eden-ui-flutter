<objective>
Ship `EdenBrandPreset` value class + `EdenBrandPresetRegistry` — the per-tenant brand-color override mechanism. Per `VERTICAL_UX_RESEARCH_2026-05-16.md` §2.4.3:

> Independent of profile (one profile, many brand presets). Today `EdenColors.presets` ships 7 MaterialColors (gold, blue, emerald, purple, red, slate, cyan). Extend to vertically-flavored presets [...]. Tenant onboarding picks profile + preset.

**Public API surface:**

```dart
@immutable
class EdenBrandPreset {
  const EdenBrandPreset({
    required this.id,
    required this.displayName,
    required this.color,
    required this.recommendedFor,
  });

  final String id;                    // 'salon-coral', 'trades-industrial-blue'
  final String displayName;           // 'Coral', 'Industrial Blue'
  final MaterialColor color;          // The brand color (existing EdenColors entry)
  final List<String> recommendedFor;  // ['salon', 'spa', 'wellness']
}

class EdenBrandPresetRegistry {
  EdenBrandPresetRegistry._();

  static List<EdenBrandPreset> all() => List.unmodifiable(_all);

  static EdenBrandPreset? byId(String id) =>
      _byId[id];

  static List<EdenBrandPreset> forVertical(String vertical) {
    final lower = vertical.toLowerCase();
    return _all.where((p) =>
      p.recommendedFor.any((v) => v.toLowerCase() == lower)).toList();
  }

  static final List<EdenBrandPreset> _all = [/* 15 presets hand-built */];
  static final Map<String, EdenBrandPreset> _byId = {
    for (final p in _all) p.id: p,
  };
}
```

<context>
**Why metadata-distinct presets over color-distinct:** the value of a brand-preset registry is two-fold — (1) consumer apps surface a "Choose brand" dropdown to tenants with semantically-relevant options ("Federal Navy" for a gov tenant, NOT "Blue" generically), and (2) per-vertical filtering so the dropdown shows tenant-relevant options first. Both behaviors come from the metadata (id + displayName + recommendedFor) — the COLOR can repeat. Adding 8 new MaterialColor definitions for these v1 presets would balloon `EdenColors` without changing the user-visible rendering vs `EdenColors.red`. Defer to v2 when concrete tenant feedback drives concrete hex variations.

**Why a static registry vs runtime register/add:** v1 ships a closed set. Per OBJECTIVE.md Constraint 11 (locked profile values) + Constraint 1 (back-compat), introducing a runtime registration API now means committing to a stable public surface for a TBD plugin pattern. Defer. Consumers needing custom brand colors today can use any `MaterialColor` directly when constructing `EdenAdaptiveTheme` in TRD 009-05 — the preset registry is convenience, not a gate.

**Why `recommendedFor` is `List<String>` not `Set<EdenVertical>`:** v1 has no `EdenVertical` enum. Verticals are loose tags. A `List<String>` is forward-compatible with future enum migration AND lets downstream apps add their own tags (e.g., `'aohealth'`) without library changes. The string-tag pattern is consistent with how `tags` are handled elsewhere in eden-ui-flutter (per existing widget patterns; not a novel introduction).

**Why no `EdenBrandPresetRegistry.add(preset)` runtime API:** YAGNI. v1 doesn't need it. Adding it commits to a mutability contract that's hard to walk back. Downstream apps wanting custom presets can hold their own `List<EdenBrandPreset>` and feed it into `EdenAdaptiveTheme` directly — the library doesn't need a singleton.

**Why ids are kebab-case not camelCase:** matches the existing `EdenColors.presets` map keys (`'gold'`, `'blue'`, not `'edenGold'`). Kebab-case is also what tenant config files typically use (YAML/JSON friendly). Consistency.

**Donor reference:** the existing `EdenColors.presets` map (lib/src/tokens/colors.dart line 154-162) ships 7 MaterialColors keyed by short names. Bridge entries (rows 1-7 in the table) preserve those ids exactly so consumers migrating from `EdenColors.presets['gold']` to `EdenBrandPresetRegistry.byId('gold')` get the same color.
</context>

<gotchas>
- **`EdenColors.presets` map keys are LOWERCASE.** Verified by reading `lib/src/tokens/colors.dart` lines 154-162: `'gold', 'blue', 'emerald', 'purple', 'red', 'slate', 'cyan'`. The bridge entries in our registry MUST use these exact ids (rows 1-7). Drift breaks the migration path.
- **`List<String>` const-ability.** `const ['salon', 'spa']` is a const list. `EdenBrandPreset` const constructor accepts `required this.recommendedFor` as `List<String>` — to make `static const` instances of `EdenBrandPreset`, all `recommendedFor` arguments must be `const [...]` literals. Verified: passing `const ['salon', 'spa', 'wellness']` to a const constructor compiles.
- **Duplicate id check.** The registry assertion runs at first access (static field initialization). If two presets share an id, the `_byId` map collapses them — last one wins. Add a defensive `assert(_byId.length == _all.length, 'Duplicate preset id detected')` in a static initializer / first-access guard. Lint-friendly approach: an internal helper method that runs once.
- **Case sensitivity in `forVertical`.** `'salon'` vs `'Salon'` must match — implement `vertical.toLowerCase()` comparison. The fixture data uses all lowercase already; this is defense against caller typos.
- **`List.unmodifiable` vs returning the internal list directly.** Returning the internal `_all` directly lets callers mutate it (e.g., `EdenBrandPresetRegistry.all().add(...)`). Wrap in `List.unmodifiable(_all)` to prevent — the unmodifiable list is a shallow read-only view.
- **`recommendedFor` lookup is a linear scan.** For 15 presets × N callers, this is fine. Don't pre-build an inverted index — premature optimization. If consumers report perf issues at 50+ presets, revisit.
- **Hand-built means HAND-TYPED.** Per OBJECTIVE.md Constraint 4 + Playbook habit 4: do NOT generate the 15-row table via LLM. Type them line-by-line from the table in `<objective>`. The fixture file's `// Do NOT regenerate via LLM` header is the contract.
</gotchas>

@immutable
class EdenBrandPreset {
  const EdenBrandPreset({

    required this.displayName,
    required this.color,

  /// Non-empty by contract; at least one tag per preset.
  final List<String> recommendedFor;
}

    final map = <String, EdenBrandPreset>{};
    for (final p in _all) {
      assert(!map.containsKey(p.id),
          'Duplicate EdenBrandPreset id detected: ${p.id}');
      map[p.id] = p;

    final lower = vertical.toLowerCase();
    return _all

            .any((v) => v.toLowerCase() == lower))
        .toList();
