<objective>
Extend `EdenAdaptiveTheme` so a downstream app can build a full Eden theme from values it
only learns at runtime, composing all three capabilities from this objective.

Purpose: capabilities 1-3 (TRDs 022-02/03/04) are ingredients. Without an entry point
that accepts them, a downstream app has a swatch, a profile-data object and a font string
but still cannot build a theme — `EdenAdaptiveTheme.light()` only takes the `const` enum.
022-CONTEXT.md finding 4 names `EdenAdaptiveTheme` as "the right seam to extend", and
LOCKED decision 2 requires extending it rather than forking a parallel runtime path.

This is the TRD that TRD 022-01's byte-identity spine was written to protect.

Output: a data-taking core, the existing statics refactored to delegate to it, and a
config-shaped convenience pair.
</objective>

  static ThemeData light(
    EdenThemeProfile profile, {
    EdenBrandPreset? brand,
  }) {
    final resolvedBrand = brand?.color ?? profile.data.primaryColor;

And the overlay helper, which currently takes the enum and reaches through `.data`:

```dart
  static ThemeData _withProfileTextTheme(
    ThemeData base,
    EdenThemeProfile profile,
  ) {
    final data = profile.data;
    if (data.bodyFontFamily == null && data.displayFontFamily == null) {
      return base;
    }

    final body = base.textTheme;
    final displayOverlay = EdenProfileFonts.displayTextStyle(profile);
    final bodyOverlay = EdenProfileFonts.bodyTextStyle(profile);
    final overridden = body.copyWith(
      displayLarge: body.displayLarge?.merge(displayOverlay),
      ...
      labelSmall: body.labelSmall?.merge(bodyOverlay),
    );
    return base.copyWith(textTheme: overridden);
  }
```

Note the documented merge direction — preserve it verbatim when converting to
data-taking:

```dart

  /// supplies fontSize / fontWeight / height; the OVERLAY supplies fontFamily.
```

<anti_patterns>
- DO NOT add a second theming class (`EdenRuntimeTheme`, `EdenBrandTheme`, ...). LOCKED
  decision 2: "Extend `EdenAdaptiveTheme`, do not fork it. One theming entry point. A
  second 'runtime' path that diverges from the static one is the failure mode to avoid."
- DO NOT leave `_withProfileTextTheme` in place alongside a new `_withDataTextTheme`.
  Convert the one helper to take data and have the enum path reach it through
  `profile.data`. Two overlay helpers WILL drift.
- DO NOT change the signatures of `EdenAdaptiveTheme.light(profile, {brand})` or
  `.dark(profile, {brand})`. Objective 009's tests, the dev_app catalog screens
  (`lib/dev_app/screens/theme_profiles_screen.dart`, `lib/dev_app/explorer/*`) and the
  widget `build()` all call them.
- **DO NOT add a `monoFontFamily` parameter to `lightFromConfig` / `darkFromConfig` /
  `_configData`.** This is the objective's headline entry point and the rule from
  022-CONTEXT.md § Out of scope applies to it in as many words: *"Adding a token here
  that still reaches nothing would be worse than leaving it declared, because it would
  look finished."*

  MEASURED 2026-08-26: `EdenProfileFonts.monoTextStyle` has ZERO production call sites in
  `lib/` — the only other `monoFontFamily` hits are `lib/src/widgets/eden_blame_view.dart`,
  an unrelated widget parameter that defaults to the literal `'monospace'` and never
  consults `EdenProfileFonts` at all. And `_withDataTextTheme` overlays body and display
  roles only, because Material's `TextTheme` has no mono role to overlay. So
  `lightFromConfig(monoFontFamily: 'Fira Code')` would return a `ThemeData` byte-identical
  to `lightFromConfig()`. A partner would set it, see nothing change, and have no way to
  tell whether they had mistyped the family name.

  The distinction that decides this: a DATA FIELD a consumer reads is honest (that is why
  `EdenThemeProfileData.runtime` keeps `monoFontFamily`, and why objective 510 wired
  `BRAND_FONT_MONO` into its resolver for contract completeness with a unit test pinning
  that it renders nothing). A THEME ENTRY-POINT PARAMETER implies it themes something.
  This one would not. Mono's real route stays open and unchanged:
  `EdenProfileFonts.monoTextStyleForFamily(family)` from TRD 022-04, called by the
  consumer's own widget.
- DO NOT re-resolve the brand as `brand?.color ?? somethingElse` in more than one place.
  Fold it into the data object once, then pass the data down.
- DO NOT hand a `Color` where a `MaterialColor` is expected. `EdenTheme.dark()` does
  `primary[950]!`; a plain `Color` has no shades and the app dies at boot.
- DO NOT touch `surfaceTonalSeed`, `radiusMultiplier`, `minimumTouchTargetPx` or
  `preferBorderOverShadow`, and do NOT add a `ThemeExtension` to carry them. That is
  Objective 0b — 165 of 314 widget files read `EdenRadii.*` as static constants and 184
  files reference `EdenColors` directly. Out of scope.
- DO NOT edit `test/theme/eden_adaptive_theme_test.dart` or
  `test/theme/eden_theme_back_compat_test.dart`. If either goes RED, the production
  change is wrong.
</anti_patterns>

<error_recovery>
**The refactor is provably behaviour-preserving — verify this reasoning before writing
code, and if it does not hold, stop.**

For the no-brand case, `data = profile.data`, therefore:
  - `data.profile == profile`                              -> same status palette
  - `data.primaryColor == profile.data.primaryColor`       -> same `resolvedBrand`
  - `data.bodyFontFamily == profile.data.bodyFontFamily`   -> same overlay decision

For the brand case, `data = profile.data.copyWith(primaryColor: brand.color)`:
  - `data.profile == profile`                              -> unchanged
  - `data.primaryColor == brand.color`                     -> same as `brand?.color`
  - fonts untouched by `copyWith`                          -> same overlay

So both paths feed `EdenTheme.light/dark` and the overlay exactly what they receive
today. If TRD 022-01's baseline goes RED, one of those three equalities was broken.

**If `lightFromConfig` with a bad hex throws**, `EdenBrandSwatch.tryParse` is not being
allowed to return null into `copyWith` — check that you are passing the nullable result
straight through rather than force-unwrapping it with `!`.

  ///   darkTheme: EdenAdaptiveTheme.darkFromConfig(
  ///     brandHex: config['brandHex'] as String?,
  ///   ),
  /// );
  /// ```

  /// [base]'s primary colour and an unavailable font family falls back to the Eden
  /// default — a malformed partner value must never crash an app's boot.
  ///

  /// has no mono role, so a mono family cannot be overlaid onto a [ThemeData] here —
  /// accepting one would return a theme identical to one built without it. Mono is
  /// still reachable: read [EdenThemeProfileData.monoFontFamily] (settable via
  /// [EdenThemeProfileData.runtime]) and pass it to

    EdenThemeProfile base = EdenThemeProfile.commercialWarm,
    String? brandHex,
    String? bodyFontFamily,
    String? displayFontFamily,

  static ThemeData darkFromConfig({ ...same parameters... }) =>
      darkFromData(_configData(
        base, brandHex, bodyFontFamily, displayFontFamily));

    EdenThemeProfile base,
    String? brandHex,
    String? bodyFontFamily,
